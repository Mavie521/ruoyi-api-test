## 五、本次最终版三大进阶优化落地（核心亮点）

### 优化1：解决「仅一次控制器」阶梯加压失效隐患

**问题根源**：

第三方阶梯线程组（Stepping Thread Group）会不断销毁旧线程、新建线程，新线程会重复触发仅一次控制器，导致大量重复登录、Token频繁刷新、业务模型失真。

**最终方案落地**：

- 当前版本使用**原生普通线程组**，仅一次控制器稳定可用；

- 预留企业兼容方案：后续如需阶梯加压，可将登录迁移至 SetUp 线程组，通过 **props全局属性** 全局共享Token，彻底规避线程重建导致的重复登录问题。

### 优化2：JDBC连接池瓶颈治理

**问题根源**：

全局JDBC连接池多线程共享，高并发下连接数不足会导致线程阻塞、压测结果失真。

**最终优化**：

- 本项目业务压测**完全不使用JDBC**，仅SetUp/TearDown低频次执行；

- 已调大连接池 Max Active 最大连接数，杜绝连接等待瓶颈；

- 架构隔离：业务施压与数据清理完全解耦，互不干扰。

### 优化3：定时器\+断言体系企业级升级

**1\. 定时器升级：普通随机定时器 → 高斯随机定时器**

均匀随机不贴合人类操作，高斯定时器为**正态分布**，大部分思考时间集中在1\-2s，少量极值，完全贴合真实用户行为。

**2\. 新增接口增加【持续时间断言 Duration Assertion】**

除校验状态码、业务码外，额外校验**接口SLA响应时长**，业务成功但超时直接判定失败，提升性能验收严谨度。

## 七、性能验收标准（SLA指标）

- 错误率 ≤ 0\.5%

- 95%响应时间 ≤ 500ms

- 写接口持续时间断言阈值 ≤ 800ms

- 服务器CPU稳态 ≤ 75%

- 内存无持续递增、无连接泄露、TPS平稳无断崖下跌

## 八、数据治理方案（企业规范）

- 压测运行中**不清理、不校验数据库**，保证压力纯净；

- 所有压测数据统一打 test\_flag=1 标记；

- SetUp 清除历史脏数据，保证环境干净；

- TearDown 全部压测结束后批量清理，不影响压测过程。
